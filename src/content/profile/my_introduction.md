## 我做技术选择的习惯

学过不等于要用，热门更不等于合适。我习惯先动手写最小实验、算清本机和线上成本，再决定要不要留下来：

- **不为低频场景背重型组件的债**：亲手跑过 Seata 分布式事务 demo 后，看清了全局锁开销和排查复杂度，业务里直接改用本地事务提交后发 MQ + 消费端幂等做最终一致性；选微服务链路追踪时，考虑到单机已经跑着十来个中间件，比完 SkyWalking 和 Micrometer Tracing + Zipkin 后选了框架原生的轻方案；做社区语义检索时，数万条向量的量级根本用不上常驻 2G+ 内存的 Milvus，而更早用 Redis 做向量也踩过坑，最后直接用栈里已有的 Elasticsearch `dense_vector` 一并收口。
- **边界切干净，不让两套技术栈各做一半**：学 Spring AI 时试过它的 `ChatClient`、注解式 Tool Calling 和本地 stdio MCP，但觉得工作流编排不如 Python 侧的 LangGraph 直观；于是索性划清界线——Java 管业务事务、权限、配额扣减与落库，Python 管图编排和模型调用，AI 服务不回头反调业务接口，避免形成循环依赖。
- **先拿证据，再定阈值和策略**：加熔断限流之前先上链路追踪，看清判题和模型调用的真实耗时分布，再去配慢调用阈值和并发隔离；做检索或模型分级也先留验证集和埋点，不在看不见数据的地方拍脑袋调参。
- **硬约束交给机制，不赌人或模型的自觉**：谁能调用什么模型、单日花多少钱，一律用代码和原子 SQL 按真实金额预占结算，绝不写进提示词指望模型遵守；给 AI 写记忆库规则总被忘，就把校验挪进 MCP 写入网关和 git `pre-commit` 钩子，让不合规的内容在落地前就被拦住。

遇到没碰过或者答不上来的问题，我会直接说不了解。比起背标准答案，我更愿意聊真实做过的判断和踩过的坑。
